# P04: Security Audit, 2026-10-16

**Scope:** MerchMate Phase 1, the deployed static PWA at https://invoice-aso-oke.vercel.app/ (source at `530a22c`, fixes in the commits below).
**Method:** code review of every data-entry path, a search of the full git history and the built bundle for secrets, `npm audit` plus a sourcemap build to see which advisories reach users, and attack tests run in headless Chromium.
**Not available:** `docs/AUDIT_STANDARD.md` does not exist; default rigor and severity (exploitability x damage) used. The Appendix items (access policies, auth settings, storage buckets, security advisor) do not apply: there is no database server, auth provider or storage bucket.

## Verdict: READY WITH FIXES (all fixes made; two items need your decision)

There is no server, account system, API or payment gateway, so the classic serious failures (broken access control, leaked service keys, injection into a database, payment tampering, IDOR) cannot occur. The real attack surface is small: **a malicious "backup" file**, **browser-side code injection (XSS)**, **the delivery chain (npm, GitHub, Vercel)** and **anyone holding the user's phone**. I found one realistic attack (a crafted backup), fixed it, and closed a header gap that left the site open to clickjacking and made any future XSS far worse. No secrets need rotating.

## Step 0: Threat model

**Assets**
1. The merchant's client list (names, phones, addresses) and bank details, stored in the browser.
2. Invoice/payment records (the merchant's financial truth) and private job costs and profit.
3. The integrity of what the merchant sends clients (a tampered invoice could redirect payments to another account).
4. The deployed app itself: whoever can change it can run code on every user's device.

**Attackers**
- Someone who sends the merchant a file or link (malicious "backup", phishing page).
- Someone with brief access to an unlocked phone (employee, family, a stolen phone).
- A page on another site (clickjacking/framing).
- A supply-chain attacker (a malicious npm package, or compromised GitHub/Vercel account).
- No malicious *users of the same system*: there are no shared accounts, so there is no other-tenant data to reach.

**Attack surface (every entry point)**

| Entry point | Untrusted input? | Result |
|---|---|---|
| Static pages and assets (`/`, `/privacy.html`, `/terms.html`, JS/CSS/icons) | no | Headers fixed (#2) |
| Service worker `/sw.js` (precache only, no runtime caching, no cross-origin) | no | OK |
| **Backup restore** (file input, `BackupCard`) | **yes** | **Fixed (#1)** |
| Logo upload (`BusinessProfileForm`, `FileReader` to data URL, 2 MB cap) | file chosen by the user | OK (#6) |
| Forms (invoices, clients, settings): typed by the owner | the owner only | Validated with zod/react-hook-form; rendered by React (auto-escaped) |
| WhatsApp / mailto links | built from the owner's data | Phone reduced to digits, text URL-encoded, `rel="noopener noreferrer"` |
| CSV export | owner's data opened in Excel | Formula-injection escaping present |
| Share / download (Web Share, blob downloads) | no | OK |
| `localStorage` (tab, backup date, error log, hint flag) | no secrets | OK |
| IndexedDB | the owner's device | See #4 |
| API routes, webhooks, auth flows, AI endpoints, admin areas, storage buckets, database policies | | **N/A: none exist** |

## Findings

### Fixed

| # | Sev | Finding | Fix |
|---|---|---|---|
| 1 | **Medium** (High if backups get shared between people) | **A crafted backup file could permanently break the app or track the user.** Restore only type-checked a handful of fields (`src/lib/backup.ts`). 13 of 16 hostile test files were accepted. | Every field the app reads is now type-checked; logos must be embedded images; colours must be `#RRGGBB`; files over 50 MB are refused. Older backups still restore. Commit `7e27954` |
| 2 | **Medium** | **No security headers.** The live site sent no Content-Security-Policy, no framing protection and no `nosniff`. It could be framed by another site (clickjacking: a hostile page overlays buttons, tricking someone into marking an invoice paid or deleting data) and, if an XSS were ever introduced, nothing would limit it. | `vercel.json` now sends a strict CSP and companion headers. Commit `3fce0bd`. Verified in a browser (see below) |
| 3 | Low | 31 `npm audit` advisories. | `npm audit fix` took it to 11, lockfile only. Commit `ab699e1`. Analysis below |

**#1 attack scenario.** (1) An attacker sends a "MerchMate backup" file (a fake "my accounts" file, a shared "template", a tampered real backup). (2) The merchant taps Restore; the old validator accepts it and *replaces all data*. (3a) With `"payments": 5` on any invoice, `getPaymentHistory` returns `5` and `5.filter` throws during render. The error boundary shows "Something went wrong"; "Try again" reloads into the same crash, because the bad data is in storage. The only way out is clearing the site's data, which also deletes any real records. (3b) With `"logoUrl": "https://attacker.example/p.png"` the app, the invoice image renderer and the PDF engine fetch that address every time a document is generated, telling the attacker when the merchant works and from what IP.
**Safe self-test:** in *Settings → Backup & Restore*, restore a backup file you edited so one invoice has `"payments": 5`. Before the fix it was accepted; now it is refused with "Backup file is damaged or incomplete" and nothing changes. `src/lib/backup-security.test.ts` contains all 16 cases (plus checks that real and older backups still restore).

**#2 attack scenario and test.** (1) Attacker hosts a page that frames `invoice-aso-oke.vercel.app` invisibly. (2) The victim, who is using the installed app in another tab, is lured to click on the attacker's page; their click lands on the framed app. **Safe self-test:** `curl -sI https://invoice-aso-oke.vercel.app/` should show `content-security-policy`, `x-frame-options: DENY`, `x-content-type-options: nosniff`.

The policy: scripts only from the app itself (no inline, no `eval`), plus `'wasm-unsafe-eval'` because the PDF layout engine compiles WebAssembly; images/fonts/connections only from the app, `data:` and `blob:`; no plugins; no framing; no base-tag changes; `upgrade-insecure-requests`. Chromium with the headers enforced: invoice PDF and image, receipt, statement, backup, problem report, logo, service worker registration and the legal pages all work with **zero violations**. A first attempt without `'wasm-unsafe-eval'` broke PDF generation, which is why this was tested before deploying. `style-src 'unsafe-inline'` remains because React and Framer Motion write inline styles; with scripts locked down this carries little risk. A test (`src/lib/headers.test.ts`) fails if anyone loosens the policy.

### Low / informational

6. **Logo upload accepts any `image/*`, including SVG.** It is stored as a data URL and only ever shown through `<img>`, a canvas or the PDF engine, none of which run scripts in an SVG, and the 2 MB cap and the CSP bound the rest. Fine.
7. **11 `npm audit` advisories remain**, all in dev tooling that never reaches users: `vite` 5 (dev server path traversal), `esbuild` (dev server accepts requests from any website), `vitest`/`tinypool` (2 critical, test runner only), and the `node-stdlib-browser` crypto chain. Only one flagged package is bundled (`vite-plugin-node-polyfills`, low, and only its small shims; the crypto code the advisory is about is not included). The fixes require major upgrades (Vite 5 to 8, Vitest 3 to 5), which I judged too risky to bundle into a security pass. **Mitigation until then:** run `npm run dev` only when you need it, on localhost (the default; never `--host`), and do not browse untrusted sites while it is running.
8. **Vercel serves static files with `access-control-allow-origin: *`.** Harmless here: they are public files and no endpoint handles user data.
9. **CSRF, SSRF, open redirects, rate limiting, auth, MFA, OAuth, session handling, AI abuse, payment webhooks, file storage policies: N/A** (no server, cookies, accounts, endpoints or gateway). The only "fetch a URL I was given" path was the logo URL in a backup, closed in #1. Server-side validation is moot: there is no server, and the equivalent (validating untrusted data at the point it enters storage) is #1.

### Checked and fine
- **XSS:** no `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `document.write`, `window.open`, `postMessage` or `location` use anywhere in `src/`; every user value is rendered through React (escaped) or canvas/PDF text.
- **Link injection:** WhatsApp numbers are reduced to digits (`toWhatsAppNumber`); messages are `encodeURIComponent`-ed; all `target="_blank"` links have `rel="noopener noreferrer"`.
- **CSV injection:** cells starting `= + - @` tab or CR are prefixed (`src/lib/csv.ts`).
- **Prototype pollution via a crafted backup (`__proto__`, `constructor`):** tested, not possible.
- **Secrets:** no `.env` ever committed (only `.env.example`, with empty values); the full history of 56+ commits was searched for keys, tokens and JWTs; the production bundle contains none. Nothing reads `import.meta.env`. **Secrets to rotate: none.** Note for Phase 2: `.env.example` names `SUPABASE_SECRET_KEY`. A secret/service key must never be given a `VITE_` prefix or used in the browser; the Supabase *anon* key is public by design, protected by access rules.
- **Supply chain:** 64 packages ship to browsers, all well-known; the unusual names (`jay-peg`, `hsl-to-rgb-for-reals`, `media-engine`, `dfa`, `restructure`, `bidi-js`) are all dependencies of `@react-pdf/*` (checked with `npm ls`). Every lockfile entry resolves from `registry.npmjs.org` with an integrity hash. Install scripts exist only for `esbuild` and `fsevents` (both expected).
- **HTTPS:** enforced with HSTS (`max-age=63072000; includeSubDomains; preload`); `http://` redirects to `https://`.
- **Error responses:** Vercel's plain 404; the app logs no personal data (problem reports exclude names, phones, amounts).
