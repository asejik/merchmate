### Open: low / nice-to-have

- **Unused code and dependencies (listed for approval, nothing removed).** Checked for dynamic references: none.
  - `date-fns`: no imports anywhere in `src/`.
  - `autoprefixer`, `postcss`: no `postcss.config`, Tailwind v4 uses its Vite plugin.
  - `src/assets/react.svg`: not referenced.
  - `InvoiceStatus` member `'draft'` (`types/index.ts:3`): nothing creates it.
  - Stale comment on `logoUrl` ("Blob URL ... temporarily", `types/index.ts:15`): it is a data URL.
- **Outdated.** Patch/minor available: dexie 4.2.1 → 4.4.6, vite-plugin-pwa 1.2.0 → 1.3.0, react-hook-form 7.70 → 7.90, tailwindcss/@tailwindcss/vite 4.1.18 → 4.3.3. Majors behind (vite 5 → 8, vitest 3 → 5, zod 3 → 4, framer-motion 11 → 14, `@react-pdf/renderer` 3 → 4, etc.) were not evaluated for migration cost; React stays 18.3.1 by constraint. Vulnerabilities belong to P04. `caniuse-lite` data is 10 months old.
- **Performance.** Main chunk 194 kB gzip is acceptable once cached but noticeable on a first load over slow mobile data; the PDF engine is lazy but precached on install (about 2 MB background download, deliberate for offline PDFs). I did not measure per-dependency size or Core Web Vitals on a device. `db.invoices.toArray()` full scans in `Dashboard.tsx:19`, `InvoiceForm.tsx:81` (number lookup on every form open), `CustomerList.tsx:21` are fine for hundreds to low thousands of invoices; revisit if a user reaches tens of thousands.
- **`isSynced` is indexed (`db/index.ts:23,29`) but booleans are not valid IndexedDB keys**, so the index never contains anything. Harmless. Schema rule says do not edit old versions; drop it in a future version block when Phase 2 reshapes the table.
- **Hardcoded defaults:** currency `'NGN'` (`InvoiceForm.tsx:110,141`), quote validity 30 days (`:104`), terms text (`invoice.ts` `DEFAULT_INVOICE_TERMS`). Reasonable for now; move to `BusinessProfile` when non-Nigerian users appear.
- **Money is stored as decimals rounded to 2 places (`round2` everywhere), not integer kobo.** Rounding is centralised and heavily tested, and a migration to integers would touch every record, so I would not change it. Currency is stored on every invoice.
- **21 blocking `alert()`/`confirm()` calls** (UX, P05).
- **Doc drift.** `README.md` says numbering "continues from your highest invoice number" (code follows the most recent, `invoice.ts` `nextInvoiceNumber`), says "Data syncs locally", still has a "Vercel URL" placeholder and placeholder screenshot, and does not list Phase 1 features added since (order stages, payment plans, costs). `.env.example` documents Supabase variables but no code reads any env var (`import.meta.env` is unused), so nothing is needed to redeploy today. Your uncommitted edit renames them to non-`VITE_` names, which is the right direction for a secret key (security belongs to P04).

### Checked and fine

- **Schema vs code.** Types match the four tables; migrations are additive v1 → v2 → v3 and the v2 backfill is now covered by a test against a real v1 database. Database name unchanged.
- **Status handling.** Stored statuses `pending/partial/paid` are derived from payments; `overdue`, `open`, `expired`, `converted` are derived at read time. Every path I traced has a transition and a display. Overpayment is confirmed by the user and capped for revenue.
- **Receipt numbers are stable** (confirmed transfers move to the end; confirmed payments cannot be removed).
- **Backup/restore** is a single transaction, zod-validated with date revival; round-trip now tested.
- **No network calls at all** in `src/` (no fetch/XHR/analytics/sentry), so there is nothing to time out, no third-party failure modes, no secrets in the bundle, and no personal data leaves the device except through the user's own share action.
- **Logs:** no `console.log`/`debugger`; `console.error` only in catch blocks and it logs errors, not user data.
- **Manifest/PWA:** separate `any` and `maskable` icons, 192/512, apple-touch icon, `start_url`/`scope` `/`, offline navigation fallback, PDF chunk precached.
- **Dev/prod separation, payment test/live keys, webhooks, idempotency, chargebacks:** not applicable (no backend, no payment gateway; payments are manual records and the unconfirmed-transfer feature is the reconciliation aid).

## 7. Platform readiness (PWA)

Covered above (#6, checked and fine). One residual risk for the future: if a release bumps the Dexie version and has to be rolled back, the older code cannot open the newer database (`VersionError`). The app now shows the storage-error screen instead of a blank page, but data would stay unreachable until the newer version is redeployed. Treat schema bumps as one-way.

## 8. Compliance and audit trails

Customer data (names, phones, addresses) is stored only on the merchant's own device; MerchMate has no server and the app sends nothing, so the merchant is the data controller and the operator holds no user data. Gaps: no in-app "erase all data on this device" (a user selling their phone must clear browser data by hand), backups are unencrypted (#10), no deletion record (#8). Admin roles do not exist, so the append-only admin log in the brief does not apply.
