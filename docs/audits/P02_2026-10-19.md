# P02: Egress & Efficiency Audit, 2026-10-19

**Scope:** MerchMate Phase 1 at `45e4518`, the static PWA at https://invoice-aso-oke.vercel.app/.
**Method:** measured the production build (raw and Brotli sizes), the service worker's precache list, and the live cache and compression headers with `curl -I`; read the data-access code; built twice to test whether identical code gives identical files. **No usage dashboard data was available**, so every projection below is an **estimate** from those measurements.
**Not available:** `docs/AUDIT_STANDARD.md` does not exist; default rigor and severity used.

## Verdict: HEALTHY (two Low findings fixed, projection far below any limit)

Most of this audit does not apply. MerchMate has no database service, auth server, realtime channel, serverless function, AI call, SMS/email provider or media storage: the data lives in the browser, PDFs and images are made on the device, and WhatsApp messages are plain links. The only usage-billed thing is **Vercel's bandwidth for serving the app's own static files**. That cost is small and mostly paid once per user.

| Moment | Download | Detail |
|---|---|---|

## Findings

| # | Sev | Finding | Status |
|---|---|---|---|
| 1 | Low | **The build time was stamped into the main script**, so identical code produced a different file on every build (checked: two builds a minute apart gave `index-CDkdNCro.js` and `index-DtAVRkTy.js`). Since every push to `main` deploys, each docs, test or CI commit (9 commits since 16 October) made every installed app download about 190 KB and show "update available" for nothing. | **Fixed**: the version shown in Settings and in problem reports is now a short id of the `src/` folder (`git rev-parse HEAD:src`), so it only changes when the code does. Verified below |
| 2 | Low | **Hashed build files were served with `cache-control: public, max-age=0, must-revalidate`** (live check on all 7 files). Files whose names contain a content hash never change under the same name, so browsers had to ask the server again on each visit that did not go through the service worker (a first visit, a returning iPhone Safari user whose storage was cleared, a browser without service worker support). The answer is a tiny 304, but it is a request and a delay each time. | **Fixed**: `vercel.json` now sends `public, max-age=31536000, immutable` for `/assets/*` only. HTML, `sw.js` and the manifest stay revalidated so a new deploy is found at once. A test (`headers.test.ts`) guards both halves. **Verify after deploy** (below) |
| 3 | Informational | The icons are 347 KB of the 1.0 MB install. A lossless re-encode saved 0 bytes (they are already optimal); smaller would mean lossy colour reduction that changes how the icon looks. | Not done |
| 4 | Informational | The main script (178 KB Brotli) holds both the app code and its libraries (React, Dexie, forms, animation). Putting the libraries in their own file would let app-only updates skip them and cut an update from about 190 KB to well under half (**not measured**). At the projected scale this saves megabytes per month in total. | Not done: not worth the extra moving parts yet. Revisit if bandwidth shows up in the Vercel dashboard |

### Checked, nothing to fix
- **Compression:** every text file is served Brotli (`content-encoding: br`).
- **A. Media:** no images are served to users beyond the icons; the logo never travels; PDFs/images are generated on the device and not re-downloaded. A logo stored as base64 in the browser database is deliberate (offline PDFs) and capped at 2 MB; it costs no bandwidth.
- **B. Auth traffic, E. Realtime, F. Third-party and AI:** N/A, none exist.
- **C. Fetching:** the app makes no network requests for data (`fetch`/XHR/WebSocket do not appear in `src/`; the CSP would block them). `useLiveQuery` reads the local browser database. The invoice list reads all invoices and clients on each change: local CPU only, a P03 matter.
- **D. Payloads:** nothing is sent anywhere. The only growing thing is the local database.
- **G. Hosting:** no functions, no image optimisation, no server rendering.
- **Offline cost of a lazy PDF engine:** the 339 KB engine is downloaded by the service worker in the background once, not on the first screen, so it does not delay first use.

## Projection (estimate)

Assumptions: 4 code-changing deploys a month (each costs an active user about 0.19 MB), every user installs once, and a returning iPhone Safari user may re-download the 1.0 MB after Apple clears unused sites' storage (about a week), which is the worst case.

| Active users | First month (everyone new) | Steady month | Worst case (everyone re-downloads weekly) |
|---|---|---|---|
| 1 | about 1.8 MB | about 0.8 MB | about 5 MB |
| 100 | about 0.2 GB | about 0.1 GB | about 0.5 GB |
| 1,000 | about 1.8 GB | about 0.8 GB | about 5 GB |
| 10,000 | about 18 GB | about 8 GB | about 50 GB |

Vercel's free (Hobby) plan has included about 100 GB of data transfer a month, and its terms limit it to personal, non-commercial use; **check both on your Vercel plan page, I could not see them from here.** Bandwidth is not the first limit you will meet at any realistic size: if you charge money for the app, the plan terms are, long before 10,000 users. Bots and scrapers hitting the site also use bandwidth (that is P04's area).

## Verify (after the fixes are deployed)

1. **Headers:** `curl -sI https://invoice-aso-oke.vercel.app/assets/<any file in the page source>` should show `cache-control: public, max-age=31536000, immutable`; `curl -sI https://invoice-aso-oke.vercel.app/sw.js` should still show `max-age=0, must-revalidate`.
2. **Network tab (F12 > Network, disable "Disable cache"):** the first visit transfers about 1.0 MB. Reload twice: the hashed files should now say `(disk cache)` instead of making a request; before the fix they made a request each time.
3. **No needless updates:** after the next docs-only push, installed apps should not offer an update, and `index-*.js` keeps its name.
4. **Dashboard:** in Vercel > Usage, "Fast Data Transfer" per month should stay near the table above. Re-check after 7 days of real usage.

## Quick check you can do yourself
Open the app, press F12, go to Network, and use it for two minutes: after the first load there should be no requests at all while you create, edit and share. Anything that keeps firing is a leak (none expected).
